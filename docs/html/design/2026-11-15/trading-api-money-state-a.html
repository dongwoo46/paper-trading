1. 무엇이 문제인가

trading-api 전체를 감사해 문제 646건을 찾았습니다(PR #52로 머지). 고치는 순서는 네 갈래로 정했고, 그중 A는 사용자 돈이 실제로 틀어지는 버그입니다.

flowchart LR
  AUD["전수 감사 646건"] --> A["A 돈·상태 결함
(지금)"]
  A --> B["B 트랜잭션 안 외부 호출"]
  B --> C["C 포트 도입"]
  C --> D["D 도메인·영속 분리"]

A의 핵심 원인은 하나입니다. 체결 금액과 잠금 해제액을 서비스(ExecutionProcessor, OrderCommandService)가 제각각 계산하고 있었습니다. 그래서 같은 돈을 두 곳이 다른 식으로 계산했고, 부분 체결이 끼면 숫자가 어긋났습니다.

부분 체결은 KIS 모드에서만 생깁니다. LOCAL은 남은 수량을 한 번에 체결합니다. 그래서 A1과 A2의 버그는 주로 KIS 계좌에서 돈을 틀어지게 합니다.

2. 설계 결정

1. 체결 금액은 주문이 스스로 계산한다

지금은 서비스가 평균 체결가를 계산해 주문에 넘기고, 주문은 총액을 평균가 × 수량으로 다시 만듭니다. 이 과정에서 총액이 틀어집니다.

채택: Order.applyExecution(수량, 체결가, 수수료)가 총액에 수량 × 체결가를 더하고 평균가도 직접 계산해서, 이번 체결 금액을 돌려줍니다. 서비스는 돌려받은 금액만 씁니다.

기각: 서비스가 체결가만 넘기게 이름을 바꾸는 안은 평균가 계산이 서비스에 남아 같은 버그가 반복됩니다. 체결 내역 합계를 매번 조회하는 안은 구조 변경이라 D 갈래로 미뤘습니다.

2. 잠금 해제액은 한 곳에서만 계산한다

최종 체결과 취소가 서로 다른 식으로 해제액을 계산했습니다.

채택: 둘 다 Order.remainingLockedAmount()(잠금액 − 누적 체결금액, 0 하한)만 씁니다. A1은 최종 체결 쪽, A2는 취소 쪽을 바꿉니다.

기각: 계좌가 주문을 읽어 해제하는 안은 애그리거트(한 묶음으로 일관성을 지키는 객체 단위) 경계를 넘습니다. 주문별 잠금을 따로 저장하는 안은 스키마 변경이라 범위 밖입니다.

3. 기계 검사를 늘리지도 숨기지도 않는다

ArchUnit 동결 저장소(이미 있는 위반 목록)와 린트 기준선은 새 위반이 생기면 빌드를 실패시킵니다.

채택: 새 메서드로 옮기거나 서명을 바꾸지 않고 기존 메서드 안에서 고칩니다. A1에서는 고쳐서 사라진 위반 1줄을 사람 승인을 받아 손으로 지웠습니다. 매수·매도 원장 저장은 한 곳으로 합쳐 저장 호출 수를 3개로 유지했습니다.

기각: 저장소 갱신 옵션으로 한꺼번에 다시 쓰는 안은 새 위반까지 함께 묻힐 수 있습니다.

4. 돈과 반올림

돈 흐름 중간에는 반올림을 넣지 않습니다. 누적 체결금액은 수량 × 체결가를 더하기만 하고, BigDecimal 곱셈과 덧셈은 정확합니다. 잠금 해제액도 뺄셈뿐입니다.

반올림을 피할 수 없는 자리는 두 곳뿐이고, 둘 다 규칙을 한 곳에 명시합니다.

자리왜 피할 수 없나규칙
수수료70,001원 × 0.000015 = 1.050015원처럼 원 미만이 나오는데, 예수금은 원 단위임체결 건별 원 미만 절사(FeePolicy 한 곳, 잠정)
평균 체결가100원 ÷ 3주처럼 끝없는 소수가 나와 자릿수를 정하지 않으면 나눗셈이 실패함소수 4자리. 표시용이고 돈 계산에는 쓰지 않음
원 미만 절사의 근거는 삼성증권 수수료 안내의 "원미만 절사"와 국고금 관리법 제47조 2항입니다. KIS의 규칙과 건별·일별 단위는 아직 확인하지 못해 "잠정"으로 둡니다.
