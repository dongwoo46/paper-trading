# 06. 오케스트레이션 흐름 (전체 파이프라인)

이 문서는 **하나의 기능(Phase)이 시작부터 PR까지** 어떻게 도는지,
그리고 그 상태를 어디에 어떻게 저장하는지 설명합니다.

---

## 1. 한 Phase의 표준 5단계

기본 Phase는 보통 **5 step**으로 구성됩니다. (간단=3, 복잡=6~7)

```
Step 1  기획      Service/Quant Planner  → spec.md + step-2..N.md 생성
   │  (승인 게이트: 사용자 승인 전엔 다음 단계 못 감)
Step 2  구현      Full Stack / Quant Dev → TDD 구현
Step 3  테스트    Test Engineer          → 기능 스코프 테스트 + 커버리지
Step 4  리뷰      Code Reviewer          → 🔴/🟡/🟢 판정
Step 5  정리/PR   Orchestrator(Cleanup)  → 전체 테스트 → summary → PR
```

각 단계는 **독립된 서브에이전트**가 빈 컨텍스트로 수행하고,
끝나면 정해진 **Completion Report**를 반환합니다.

---

## 2. 전체 실행 흐름도

```
              ┌─────────────────────────────────────────┐
사용자 ──▶  /orchestrate                                  │
              │                                           │
              ▼                                           │
        docs/state.md 읽기  ── idle? ──▶ TODO.md 제시 → 사용자 선택
              │  (모드·활성 Phase)         → worktree 생성 → phase 폴더 생성
              ▼                                           │
        index.json 읽기 (current_step 확인)               │
              │                                           │
              ▼                                           │
   ┌── 모드 체크 ──┐                                       │
   │ manual: 요약 → "진행할까요?" 대기                       │
   │ auto:   즉시 서브에이전트 호출                          │
   └──────┬───────┘                                       │
          ▼                                               │
   step-N.md 전체 내용을 Agent 도구로 전달                   │
   (서브에이전트는 독립 컨텍스트 → 필요한 파일 전부 명시돼 있어야 함)
          │                                               │
          ▼                                               │
   서브에이전트 작업 → ## Completion Report 반환             │
          │                                               │
          ▼                                               │
   ┌── 결과 평가 ──┐                                       │
   │ PASS    → docs 갱신 → 다음 step 호출 ──────────────────┘  (루프)
   │ RETRY   → 실패내용 기록 → rework step 생성 → 라우팅
   │ BLOCKED → blocker 기록 → 중단 → 사용자에게 알림 (notify 훅)
   └───────────────┘
          │
          ▼ (마지막 step 완료)
   전체 테스트 게이트 → summary 작성 → phase→done 이동 → PR 생성
```

## 3. 상태는 어디에 저장되나 (단일 진실 공급원)

세션이 끊겨도 정확히 재개할 수 있도록, 상태는 **루트 `docs/`**에만 영속화됩니다.

### `docs/state.md` — 현재 상황 한눈에
```markdown
## 모드          ← manual / auto  (notify·on-stop 훅이 읽음)
## 상태          ← idle / in_progress / blocked …
## 완료된 Phase
## 마지막 액션
## 다음 액션
```

### `docs/phase/{project}/{feature}/index.json` — 상태 머신
```json
{
  "status": "in_progress",
  "current_step": 2,
  "total_steps": 5,
  "branch": "feature/{project}-{feature}",
  "worktree_path": ".worktrees/{project}-{feature}",
  "steps": [
    { "id": 1, "agent": "service-planner", "status": "completed", "result": "..." },
    { "id": 2, "agent": "fullstack-dev", "status": "in_progress",
      "substeps": [ { "id": 1, "name": "Order Aggregate", "status": "completed" } ] }
  ],
  "blockers": []
}
```

- **substeps**: 개발/테스트 에이전트는 작업을 잘게 쪼개 substep으로 기록 → 중단돼도 "substep N부터 재개".
  - **DDD 규칙: 1 Aggregate Root = 1 substep**.
- **매 step 후 오케스트레이터가 index.json + state.md를 반드시 갱신** → 이것이 세션 재개의 핵심.

## 4. 두 가지 안전 패턴

### (A) 2-pass 기획 + 승인 게이트
기획자는 한 번에 문서를 완성하지 않습니다.
```
Pass A: 코드(graphify) 읽기 → 구조화된 질문 목록 + 옵션만 제시
   ↓ (오케스트레이터가 사용자와 Q&A)
사용자: 결정 확정
   ↓
Pass B: 확정된 결정만으로 spec.md + step 문서 작성
   ↓
승인 게이트: 사용자 승인 전엔 Step 2(구현) 진입 금지
```
> 핵심: AI 해석과 사용자 의도의 **엄격한 일치**. 독단적 결정 방지.

### (B) 컨텍스트 격리
각 서브에이전트는 이전 단계 결과를 자동으로 못 봅니다. 그래서 step 문서에 항상:
```markdown
## Files to Read
- CLAUDE.md                ← 항상
- docs/ADR.md              ← 항상
- docs/phase/.../spec.md
- {이전 단계에서 만든 모든 파일 경로}
```
> 컨텍스트를 격리해 비용을 줄이고, "읽을 파일 명시"로 누락을 방지합니다.

## 5. 작업 공간 격리 (Git Worktree)

각 Phase는 별도 worktree에서 **코드만** 작업합니다. **문서(`docs/`)는 항상 메인 루트에 기록.**

```bash
# Phase 시작
git worktree add .worktrees/{project}-{feature} -b feature/{project}-{feature}
# PR 후 (cleanup)
git worktree remove .worktrees/{project}-{feature}
```

| 구분 | 위치 |
|------|------|
| 코드 작업 | `.worktrees/{project}-{feature}/` (격리) |
| 상태·문서 | 메인 루트 `docs/` (절대 worktree 안에 쓰지 않음) |

## 6. 에러 처리 매트릭스 (요약)

| 실패 유형 | 1차 대응 | 2차 | 3차(한계) |
|-----------|---------|-----|-----------|
| 테스트 실패 | 자가수정 1회 | dev 재작업 step | blocked → 사용자 |
| 리뷰 🔴 | dev 재작업 | 2차 리뷰 | blocked → 사용자 |
| 빌드/컴파일 실패 | dev 즉시 수정 | 재작업 step | blocked → 사용자 |
| 설계 오류 | planner가 spec 재작성 | — | blocked → 사용자 |
| 에이전트 무응답 | 같은 step 1회 재시도 | 사용자 보고 | blocked |
| **같은 step 3회 실패** | — | — | **blocked → 사용자 개입** |

`retry_count`는 3에서 막힙니다. 긴급정지("stop") 시 step/phase를 `paused`로 표시 후 중단.

---

## 7. 모드: auto vs manual

| 모드 | 동작 |
|------|------|
| `manual` | 단계마다 요약 → "진행할까요?" 승인 대기. (notify 훅이 알림) |
| `auto` | 승인 게이트 제외하고 자동 진행. 실패 시 멈추고 근본 원인 보고. |

사용자가 "auto"/"manual" 입력 시 즉시 `state.md`에 반영. **정리(cleanup) 단계는 항상 manual.**

---

## 8. 전체를 한 문장으로

> **사용자는 `/orchestrate`를 부르고 의사결정만 한다.
> 오케스트레이터가 `docs/` 상태를 읽어 적절한 서브에이전트(기획→구현→테스트→리뷰→정리)를 차례로 호출하고,
> 각 단계 결과로 상태를 갱신하며, 훅이 안전·검증·알림을 자동 처리한다.
> 세션이 끊겨도 `docs/`만 있으면 정확히 이어서 재개된다.**
