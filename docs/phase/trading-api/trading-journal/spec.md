# Trading Journal Automation

## Core Feature
체결 이벤트를 기반으로 계좌별 거래 일지를 자동 생성하고, 사용자가 사후 보완 메모를 남길 수 있는 조회/수정 API를 제공한다.

## Considerations
- 기존 코드베이스에는 `TradingJournal` 엔티티/리포지토리가 있으나 애플리케이션/프레젠테이션 계층이 비어 있으므로 이를 연결한다.
- 금융 안전 규칙에 따라 금액/수익률 계산은 `BigDecimal`만 사용하고, 자동 생성은 멱등하게 처리한다.
- 주문/체결/정산 도메인과 결합되므로 생성 트리거는 `ExecutionFilledEvent` 기반으로 둔다.
- 현재 워크트리에는 `backend/trading-api/graphify-out/graph.json`이 없고 메인 루트(`backend/trading-api/graphify-out/graph.json`)에만 존재함을 확인했다.

## Ambiguities To Clarify
1. 자동 생성 시점은 체결 직후(near real-time)로 고정할지, T+2 정산 완료 이후 보정 생성까지 허용할지?
2. 하나의 주문에 다회 체결이 발생할 때 일지 단위를 `execution` 기준으로 둘지, `order` 기준으로 1건 upsert할지?
3. 사용자 수정 허용 범위는 `title/content/sentiment`만인지, `journalType/ticker`까지 허용할지?
4. 삭제 정책은 hard delete 허용인지, soft delete(`deleted_at`)가 필요한지?
5. 요약 조회 API의 기간 기본값과 최대 조회 범위(예: 1년 제한)가 필요한지?

## Trade-offs
- Option A: `execution_id`별 일지 1건 생성
  - 장점: 체결 단위 분석 정확도 높음.
  - 단점: 분할 체결 종목에서 일지가 과도하게 증가.
- Option B: `order_id`별 일지 1건 유지 + 최신 체결 기준 업데이트 (선택)
  - 장점: UI/사용자 관점에서 관리 용이, 노이즈 감소.
  - 단점: 체결 세부 히스토리는 별도 필드로 보관 필요.

선택: Option B. 대신 원천 추적을 위해 `entry_source_execution_id`를 저장하고, 체결 누적 값은 `summary_json`으로 기록한다.

## DDD Model
- Bounded Context: `TradingJournal` (trading-api 내부, account/order/execution read-model 소비)
- Entity
  - `TradingJournal` (Aggregate Root)
    - 식별자: `id`
    - 불변 참조: `accountId`, `orderId`, `entrySourceExecutionId`
    - 가변 속성: `title`, `content`, `sentiment`, `journalType`, `summaryJson`, `lastAutoGeneratedAt`
- Value Object
  - `JournalType` (`AUTO_ENTRY`, `AUTO_EXIT`, `AUTO_PARTIAL`, `MANUAL_NOTE`)
  - `Sentiment` (`BULLISH`, `BEARISH`, `NEUTRAL`, `REFLECTIVE`)
  - `JournalSummary` (평균단가/체결수량/실현손익 등 BigDecimal 기반 직렬화 객체)
- Aggregate
  - Aggregate Root: `TradingJournal`
  - Invariant
    - 계좌 외부 주문/체결 데이터로 생성 불가
    - `AUTO_*` 타입은 `orderId`와 `entrySourceExecutionId`가 반드시 존재
    - 동일 `orderId + journalType` 중복 금지(멱등 upsert)
- Domain Event
  - 소비 이벤트: `ExecutionFilledEvent`
  - 발행 이벤트(신규): `TradingJournalAutoCreatedEvent`, `TradingJournalUpdatedEvent`

## Implementation Approach
- Domain Layer: `TradingJournal` 필드를 FK ID 중심으로 정리(`account: Account` 객체 참조 제거), enum/VO 추가.
- Application Layer: `TradingJournalCommandService`, `TradingJournalQueryService`, `TradingJournalAutoGenerationService` 추가.
- Presentation Layer: `TradingJournalController` 및 DTO, validation, 에러 매핑 추가.
- Infrastructure Layer: `TradingJournalRepository`에 검색/업서트용 메서드, 인덱스 친화 쿼리 추가.

## Workflow
1. `ExecutionProcessor.fill()` 완료 시 `ExecutionFilledEvent` 발행.
2. `TradingJournalAutoGenerationService`가 이벤트 소비.
3. `orderId + journalType` 기준 기존 일지 조회.
4. 있으면 `summaryJson`, `lastAutoGeneratedAt` 갱신, 없으면 신규 생성.
5. 사용자 UI/API에서 조회 후 코멘트/심리 태그 수정.
6. 변경 이력은 `updated_at`, `updated_by` 감사 필드로 추적.

## API
POST /api/trading-journals/auto-generate — 체결 기반 자동 일지 생성(내부/운영용)
Request:
```json
{
  "executionId": 123,
  "idempotencyKey": "exec-123-auto-journal"
}
```
Response:
```json
{
  "journalId": 45,
  "accountId": 1,
  "orderId": 77,
  "journalType": "AUTO_ENTRY",
  "status": "CREATED"
}
```
Errors: 400(유효하지 않은 executionId), 404(체결/주문 없음), 409(멱등키 충돌)

GET /api/trading-journals?accountId=1&ticker=005930&from=2026-01-01&to=2026-05-03&page=0&size=20 — 일지 목록 조회
Response:
```json
{
  "items": [
    {
      "journalId": 45,
      "accountId": 1,
      "orderId": 77,
      "ticker": "005930",
      "journalType": "AUTO_ENTRY",
      "sentiment": "NEUTRAL",
      "title": "삼성전자 진입",
      "content": "20일선 반등 확인 후 진입",
      "summary": {
        "filledQuantity": "10",
        "avgFillPrice": "82000.00",
        "realizedPnl": "0"
      },
      "createdAt": "2026-05-03T10:10:00Z",
      "updatedAt": "2026-05-03T10:10:00Z"
    }
  ],
  "page": 0,
  "size": 20,
  "total": 1
}
```
Errors: 400(기간 역전/사이즈 초과), 404(account 없음)

PATCH /api/trading-journals/{journalId} — 사용자 보완 메모 수정
Request:
```json
{
  "title": "삼성전자 재진입 복기",
  "content": "손절 기준을 2%로 더 엄격히",
  "sentiment": "REFLECTIVE"
}
```
Response:
```json
{
  "journalId": 45,
  "status": "UPDATED"
}
```
Errors: 400(빈 title/content), 404(저널 없음), 409(낙관적 락 충돌)

GET /api/trading-journals/{journalId} — 단건 조회
Response: 위 item 스키마 동일
Errors: 404

## DB
Table: `trading_journals`
- key columns
  - `id` BIGSERIAL PK
  - `account_id` BIGINT NOT NULL (FK -> accounts.id)
  - `order_id` BIGINT NULL (FK -> orders.id)
  - `entry_source_execution_id` BIGINT NULL (FK -> executions.id)
  - `journal_type` VARCHAR(30) NOT NULL
  - `ticker` VARCHAR(20) NULL
  - `title` VARCHAR(200) NOT NULL
  - `content` TEXT NOT NULL
  - `sentiment` VARCHAR(20) NULL
  - `summary_json` JSONB NOT NULL DEFAULT '{}'::jsonb
  - `last_auto_generated_at` TIMESTAMPTZ NULL
  - `version` BIGINT NOT NULL DEFAULT 0
  - `created_at`, `updated_at`, `created_by`, `updated_by`

Indexes
- `idx_trading_journals_account_created_at (account_id, created_at DESC)`
- `idx_trading_journals_account_ticker_created_at (account_id, ticker, created_at DESC)`
- `uq_trading_journals_order_type (order_id, journal_type) WHERE order_id IS NOT NULL`
- `idx_trading_journals_execution_id (entry_source_execution_id)`

Relationships
- N:1 `trading_journals.account_id -> accounts.id`
- N:1 `trading_journals.order_id -> orders.id`
- N:1 `trading_journals.entry_source_execution_id -> executions.id`

## Non-Functional Requirements
- 멱등성: 동일 이벤트 재처리 시 중복 생성 금지.
- 성능: 계좌별 최신 20건 조회 p95 < 150ms (로컬 기준).
- 감사추적: 생성/수정 사용자와 타임스탬프 보존.
- 안정성: 자동 생성 실패가 주문 체결 트랜잭션을 롤백시키지 않도록 비동기/격리 처리.
