## 3. 기능 목적

- 사용자/액터: 플랫폼 운영자 1인(본인). KIS 계좌와 토스증권 계좌를 함께 보유. `스펙`
- 사용자 문제: 지금은 KIS만 실계좌로 연결되어, 토스 계좌의 시세, 잔고, 주문을 이 플랫폼에서 다룰 수 없다. `스펙`
- 의도: 계좌마다 브로커를 하나 지정하고, 주문, 시세, 잔고, 체결이 그 브로커로만 가게 한다. 브로커가 늘어도 같은 구조에 어댑터만 추가한다. `스펙`
- 단계: `스펙`
  1. 토스 읽기 전용: 시세, 잔고, 보유 REST 조회
  2. 공통 브로커 계층으로 KIS 전면 리팩터링, 토스 읽기 기능을 같은 계층에 올림
  3. 토스 시세 웹소켓, 토스 실주문과 체결 이벤트
- 안 만드는 것 (non-goal):
  - 한 계좌가 두 브로커에 동시에 주문하는 구조, 장애 시 다른 브로커로 자동 전환 `스펙`
  - 토스 모의투자 모드. 토스 Open API에 샌드박스가 없다 `보강`
  - 토스 조건주문(SINGLE, OCO, OTO). 기존 청산 트리거와 역할이 겹쳐 이번 범위 밖 `보강`
  - 토스 랭킹, 섹터, 수급 동향 API `보강`

## 4. 사용자 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 결과 상태 |
|---|---|---|---|
| 1 | 토스 키와 허용 IP를 준비하고 환경변수에 키를 넣는다 | 기동 시 키 존재 여부 확인, 값은 로그에 남기지 않음 | 토스 연동 활성 또는 비활성 `보강` |
| 2 | 토스 계좌를 `TOSS_LIVE` 모드로 등록한다 | 토스 `GET /accounts`의 `accountSeq`와 내부 계좌를 연결 | 토스 계좌 생성 `물어봄` (FLAG-04) |
| 3 | 토스 계좌의 잔고와 보유를 조회한다 | 토스 `GET /holdings` 호출 후 내부 응답으로 변환 | 현금, 평가금액, 종목별 손익 표시 `스펙` |
| 4 | 종목 시세를 조회한다 | 토스 `GET /prices` 등 REST 호출 | 현재가 응답 `스펙` |
| 5 | (1단계) 토스 계좌로 주문을 시도한다 | 주문 분기에서 명시적으로 거부하고 이유를 응답 | 주문 생성 안 됨, 자금 잠금 없음 `스펙` (FLAG-02 결정) |
| 6 | (2단계 이후) 어떤 계좌로든 주문, 잔고, 체결을 다룬다 | 계좌의 브로커 지정에 따라 공통 포트가 해당 어댑터를 고름 | KIS와 토스가 같은 흐름 `스펙` |

## 5. 화면 상태

1단계는 백엔드 API만 만든다 (FLAG-05, ASSUME). 아래는 API 응답 상태다.

| 화면·영역 | 상태 | 트리거 | 보여줄 것·동작 | 출처 |
|---|---|---|---|---|
| 토스 잔고 API | 초기 | 토스 키 미설정 | 연동 비활성 에러, 키 이름만 안내 | 보강 |
| 토스 잔고 API | 성공 | 정상 응답 | 현금, 평가금액, 손익, 종목 목록 | 스펙 |
| 토스 잔고 API | 빈 결과 | 보유 종목 0 | 빈 목록과 현금만 | 보강 |

| 토스 잔고 API | 권한 없음 | 토스 계좌가 아닌 계좌로 호출 | 거부 | 보강 |

## 6. 정책·규칙

| ID | 규칙 | 적용 대상 | 출처 | 틀리면 impact |
|---|---|---|---|---|
| RULE-01 | 계좌 하나는 브로커 하나에만 묶이고, 주문, 잔고, 체결은 그 브로커로만 간다 | 모든 계좌 | 스펙 | 높음 |
| RULE-02 | 토스 계좌는 `TOSS_LIVE` 실계좌 모드만 있다 | 토스 계좌 | 보강 | 높음 |
| RULE-03 | 브로커 모드가 추가되면 주문 분기에 반드시 대응이 있어야 하고, 없으면 조용히 넘어가지 않고 실패한다 | `submitExternalOrderIfNeeded` 및 2단계 공통 포트 | 보강 | 높음 |
| RULE-04 | 주문 분기의 `else -> {}`를 없애고 모든 모드를 명시한다. 1단계에서 `TOSS_LIVE`는 「아직 지원 안 함」으로 거부하고, 분기 누락을 잡는 테스트를 둔다 (FLAG-02) | 외부 주문 분기 전체 (사용자 주문, 자동 청산 주문) | 스펙 | 높음 |
| RULE-05 | 토스 키는 환경변수로만 받고 로그, 응답, 커밋에 남기지 않는다 (CLAUDE.md 보안 규칙) | 설정 | 스펙 | 높음 |
| RULE-06 | 토스 토큰 발급 지점은 하나로 모은다 (토큰이 클라이언트당 1개만 유효) | trading-api, collector-api | 보강 | 높음 |
| RULE-07 | 토스 토큰은 Redis에 암호화해 저장하고, 발급은 분산 락으로 한 곳에서만 한다. 암호화 키는 환경변수로 받는다 (FLAG-01) | 토큰 관리 | 스펙 | 높음 |
| RULE-08 | 토스 호출은 그룹별 초당 한도를 지키고, 429면 `Retry-After`만큼 기다린다. 다른 브로커로 대체하지 않는다 | 토스 어댑터 | 보강 | 중간 |
| RULE-09 | 금액, 수량, 가격은 `BigDecimal`로 받고 부동소수점을 거치지 않는다 (CLAUDE.md 금융 안전) | 응답 변환 | 스펙 | 높음 |
| RULE-10 | 2단계 리팩터링은 KIS 동작을 바꾸지 않는다. 기존 KIS 테스트가 전후로 모두 통과해야 한다 | KIS 경로 | 보강 | 높음 |

## 7. 데이터·API 요구

| 필요 | 데이터·API | 요청 | 응답 | 소유 | 출처 |
|---|---|---|---|---|---|
| 토큰 | 토스 `POST /oauth2/token` | client credentials | access token, 만료 | backend | 스펙 |
| 계좌 | 토스 `GET /api/v1/accounts` | 토큰 | `accountSeq` 목록 | backend | 보강 |
| 잔고·보유 | 토스 `GET /api/v1/holdings` | 토큰, `X-Tossinvest-Account` | 종목별 상세, 합산 평가 | backend | 스펙 |
| 시세 | 토스 `GET /api/v1/prices`, `/orderbook`, `/candles` | 토큰, 종목 | 현재가, 호가, 캔들 | backend | 스펙 |
| 잔고 공통 포트 (FLAG-03) | 브로커 공통 잔고 포트 하나를 정의하고 1단계엔 토스 어댑터만 구현. KIS는 2단계에서 이 포트로 이전 | 내부 계좌 ID | 기존 `KisBalanceSnapshot`을 출발점으로 한 공통 모양 | backend | 스펙 |
| 계좌 연결 정보 (FLAG-04) | 내부 계좌와 토스 `accountSeq` 매핑 | 계좌 등록 시 | 저장된 `accountSeq` | backend | 물어봄 |
| 설정 | `TOSS_CLIENT_ID`, `TOSS_CLIENT_SECRET` 등 환경변수 (기존 `KIS_*` 이름 패턴) | 기동 시 | 연동 활성 여부 | backend | 보강 |

🟠 토스 응답의 필드 이름, 숫자 표기(문자열인지 숫자인지)는 개별 API 문서를 못 읽어 미확정이다. 1단계 구현 전에 실제 응답으로 확인한다 (FLAG-06).

## 10. 완료 기준

1단계(토스 읽기 전용)의 완료 기준이다. 2, 3단계는 1단계가 끝난 뒤 이 표에 추가한다.

| 완료 항목 | 검증 방법 | 상태 |
|---|---|---|
| 토스 토큰 발급과 갱신이 한 지점에서 동작 | 단위 테스트 (만료, `token-revoked`, 동시 요청) | 대기 |
| 토스 계좌 잔고, 보유 조회가 `BigDecimal`로 변환됨 | 단위 테스트 (고정 응답 fixture) | 대기 |
| 토스 시세 REST 조회 동작 | 단위 테스트 | 대기 |
| 401, 403, 429, 5xx를 구분한 에러 | 단위 테스트 | 대기 |
| 1단계 `TOSS_LIVE` 계좌의 주문이 명시적으로 거부됨 | 통합 테스트 (주문, 자금 잠금 미생성) | 대기 |
| 기존 KIS 테스트 전부 통과 | `./gradlew test` | 대기 |
| 실제 토스 계좌로 잔고 조회 1회 성공 | 수동 (허용 IP 등록 후) | 대기 |

- [ ] 핵심 사용자 흐름 동작
- [ ] 필요한 응답 상태 모두 처리
- [ ] 고위험 정책은 확인됐거나 ASK로 막힘
- [ ] API/데이터 요구 명시
- [ ] 예외 케이스 처리 또는 open으로 표시
