# 화면 지도 v3 (trading-web)

> 상태: 승인 · 2026-11-15 사용자 «추천안대로 승인» (FLAG-11 받지 않음, FLAG-12 차트 없음, FLAG-13 메모 넣음) · 같은 날 tech-planning API 대조(FLAG-08) 뒤 사용자 결정 FLAG-16~21 반영(§10). API 가 없어 뺀 영역은 §11 «API 대기».
> 근거: [제품 재기획](./product-replan-draft.md) 4장 단계·5장 화면 지도, 개정 `README.md` 로드맵, [사양서 v2](./inputs/screen-spec-v2.md), [기존 화면 목록](./inputs/frontend-inventory.md), [development-plan](./development-plan.md) §4-1(API 대조).
> v2 와의 관계: v2 는 «12개 화면을 한꺼번에, 가상 데이터로» 정의했다. v3 는 «단계마다 화면을 늘리고, 실데이터를 쓴다». v2 의 영역·열 정의는 그대로 쓸 수 있는 곳만 `v2 §N` 으로 가리키고, 바뀐 것만 적는다.
> 딱지: `재기획`(확정 문서에 있음) · `v2` · `보강`(이 문서가 채움, 승인 필요). API 현황 🟢 컨트롤러에서 확인 · 🟠 확인 못 함·없음. «API 대기» = API 가 없어 1차 구현에서 뺀 것(§11).

## 0. 원칙

1. 화면은 그 단계 기능이 생길 때 내비에 추가한다. 뒤 단계 화면을 «준비 중»으로 미리 두지 않는다 `재기획`.
2. 한 화면 안의 영역도 같다. 뒤 단계 데이터(전략·AI·관심 종목)가 필요한 영역은 그 단계에서 붙인다 `보강`.
3. v2 §0 공통 규칙(4상태·정렬·tone·부호 병기·주문 출처)은 그대로 구속한다. 단 §0-1·2(가상 데이터·고정 시각)는 폐기하고 서버 값·실제 시각을 쓴다 `보강`.
4. 금액·수량·가격은 서버가 준 문자열을 표시만 한다. 화면 계산 허용 범위는 FLAG-04 `재기획`(CLAUDE.md 금융 안전). 예외는 자산 추이 그래프 좌표 한 곳(FLAG-17).
5. 비밀값(앱키·토큰)은 화면에 입력하지도 보이지도 않는다. 연동 화면은 상태만 보인다 `보강`(CLAUDE.md 보안 규칙). 화면 입력이 필요하면 FLAG-11.
6. API 가 없는 영역은 가짜 데이터로 채우지 않고 1차 구현에서 뺀다. 빠진 영역은 이 문서 §11 에 «API 대기»로 남긴다 `보강`.

## 2. 공통 셸 (v2 §1 기준, 바뀐 것만)

1. 좌측 내비: 서비스명 «Paper Trading», 부제 «투자 실험실»(README 한 줄 정의) `보강`. 그룹은 §1 의 1단계 그룹.
2. 내비 보조 표시: 브로커 연동 옆 상태 점(정상/주의/오류 — 1차 구현은 KIS 시세 WebSocket 상태 기준), 수집 현황 옆 연결 상태 점. v2 의 «승인 대기 N» 배지는 5단계에 붙인다.
3. 상단 바 계좌 선택: 항목 = 계좌명 + 모드 배지(`LOCAL` / `KIS 모의`). 토스 계좌는 원장 대상이 아니어서 이 선택에 넣지 않는다 `보강`.
4. 상단 바 «데이터 기준» 시각·상태 점(v2 §1-9) 유지. 체결 SSE 끊김도 이 점에 반영한다(feature-spec EDGE-02).
5. 상단 바 엔진 요약 칩(v2 §1-10)은 3단계에 붙인다.
6. 알림 패널: 1단계 항목 = 체결, 주문 거부, 연동 오류(토큰 만료·연결 끊김), 원장 대사 불일치. 앱 내 알림 목록 API 가 없어(FLAG-08 대조) 1차 구현에서 뺀다 → §11.
7. 체결 토스트: 기존 동작(체결 SSE 수신 시 표시, 최대 5개, 자동 닫힘)을 유지한다(기존 목록 §177).
8. 테마·좁은 화면·내비 접기: v2 §1-5·12·14 그대로.

## 3. 브로커 연동 (0단계, 신규)

목적: 토스·KIS 계정이 연결돼 있는지, 계좌·잔고·시세 조회가 되는지 한눈에 보고 문제를 찾는다. 이 화면은 주문을 만들지 않는다.

영역: A 안내 줄 / B 연동 카드 / C 연결 계좌 / D 최근 호출·오류

1. A 안내 줄(고정): «연동 계정은 조회와 시세 수신에만 쓰입니다. 실계좌 주문은 지원하지 않습니다.» `재기획 7장 9번`
2. B 연동 카드: KIS 모의 1장. 토스 카드는 토스 연동 API 가 생길 때까지 숨긴다(FLAG-20). 항목(1차 구현은 채널 줄의 WebSocket 만 — 나머지는 §11 API 대기):
   - 연동 상태 배지: 연결됨 / 토큰 만료 임박 / 토큰 만료 / 미설정 / 오류
   - 토큰 만료 시각과 남은 시간
   - 마지막 성공 호출 시각, 24시간 호출 실패 수
   - 채널 줄: REST·WebSocket 각각 상태 배지·마지막 수신 시각
   - 작업: «토큰 재발급»(서버가 수행), «연결 확인»(조회 1회 시험). 실행 중 비활성 + 문구
3. B 미설정 카드: «서버 환경 변수에 인증 정보가 없습니다» + 설정 안내 문서 링크 자리. 값 입력 칸은 두지 않는다(원칙 5). 인증 정보 설정 여부를 알려 주는 API 가 없어 API 대기.
4. C 연결 계좌 표 열: 브로커(가운데 배지), 계좌번호(왼쪽, 가운데 자리 마스킹), 계좌 구분(가운데: 모의 / 실계좌·조회 전용), 예수금(오른쪽, 원), 평가금액(오른쪽, 원), 보유 종목 수(오른쪽), 조회 시각(왼쪽), 원장 연결(가운데: 로컬 계좌명 또는 «-»). 1차 구현은 KIS 모의 계좌 행만(토스 행은 API 대기).
5. C 행 작업: «다시 조회». 로컬 원장과 연결된 KIS 모의 계좌는 «계좌·포지션에서 보기»로 이동.
6. D 최근 호출·오류 표(20건) 열: 시각, 브로커, 채널(REST/WS), 동작(토큰 발급·잔고 조회·시세 구독 등), 결과(성공/실패 배지), 코드, 메시지(펼침). 필터: 브로커, 결과. 호출 로그 API 가 없어 API 대기.
7. 상태:
   - B 로딩(카드 자리표시) / 에러(«연동 상태를 불러오지 못했습니다» + 다시 시도)
   - B 토큰 만료: 카드 상단 경고 줄 + «토큰 재발급» 강조. C 의 해당 브로커 행은 마지막 값 + «조회 실패» 배지(토큰 상태 API 가 생기면 적용)
   - C 빈: «연결된 계좌가 없습니다»
   - D 빈: «기록된 호출이 없습니다»
8. API: KIS 시세 WebSocket 상태 `/api/kis/ws/health` 🟢, KIS 모의 계좌 조회 `/api/kis/account/balance` 🟢. 토큰 상태·재발급·호출 로그 🟠, 토스 연동 API 🟠(다른 세션이 만드는 중).

## 5. 계좌·포지션 (1단계)

v2 §3 을 기준으로 아래를 바꾼다.

1. A 계좌 카드: 거래 모드 배지 값을 `LOCAL` / `KIS 모의`로. 토스 계좌는 브로커 연동 화면에서만 본다 `보강`.
2. B 요약 KPI 에 «홀드 금액»(미체결 매수로 묶인 예수금)을 추가한다. 보조 문구로 «가용 예수금 = 예수금 − 홀드 금액». 값은 서버 값 `재기획 1단계`. 총자산·평가금액·미실현 손익·누적 수익률은 일별 잔고 마지막 행 값을 기준일과 함께 보인다(FLAG-19). 초기 자본·실현 손익은 API 대기.
3. C 포지션 표에 «잠금 수량»(매도 미체결로 묶인 수량) 열 추가, 수량 칸에 «매도 가능 N» 보조 줄. 서버 필드 🟢(잠금수량, 재기획 2장). 비중·당일손익 열과 합계 행은 서버 값이 없어 API 대기(합산은 FLAG-04 상 화면 계산 불가).
4. D 상세의 «전략 자동 체결 비중»은 3단계에 붙인다. 매입금액·종목 실현 손익·52주 위치는 API 대기.
5. E 원장 대사 영역(신규, KIS 모의 계좌만). 1차 구현은 KIS 잔고 조회 응답(`/api/kis/account/balance`)의 불일치 목록 표시만 한다(FLAG-18):
   - 요약: 조회 시각(응답 기준 시각), 결과 배지(일치 / 불일치 N건 / 실패), «지금 대사» 버튼(= 다시 조회, 실행 중 비활성)
   - 불일치 표 열: 구분(가운데: 로컬에만 / 브로커에만 / 수량 다름), 종목(왼쪽), 로컬 수량(오른쪽, 로컬 포지션 응답 원문), 브로커 수량(오른쪽, KIS 잔고 응답 원문)
   - 고정 안내: «불일치는 자동으로 고치지 않습니다. 원인을 확인한 뒤 처리하세요.» `보강`(CLAUDE.md «금융 상태를 암묵적으로 바꾸지 않는다»)
   - API 대기: 차이 열, 발견 시각·처리 상태(미처리/확인함)와 «확인함» 처리(서버가 처리자·시각 기록, RULE-12), 예수금·미체결 주문 대사, 대사 실행 기록(마지막 대사 시각 저장)
6. 상태: v2 §3-11 + E 조회 전(«지금 대사를 누르면 KIS 잔고와 비교합니다») `보강`, E 실패(오류 줄 + 다시 시도), E 대사 중 체결 발생 시 «다시 대사 필요»(feature-spec EDGE-08). LOCAL 계좌 선택 시 E 는 숨긴다.

## 6. 주문 (1단계)

v2 §5 를 기준으로 아래를 바꾼다.

1. A-3 «이 종목을 운영 중인 전략» 줄은 3단계에 붙인다.
2. D 주문 폼: «주문 출처: 수동» 배지 유지. «전략 자동 주문은 …» 안내는 3단계에 붙인다.
3. D 에 «주문 메모(선택)» 여러 줄 입력 추가. 거래 내역의 투자 로그(왜 샀나)가 된다 `재기획 5장`. 서버 저장 필드 🟠 → FLAG-13.
4. D 확인 단계 요약에 «잠길 수량»(매도 — 입력 수량)을 추가 `보강`. «홀드될 금액»(매수)은 서버 계산이 필요해 6-5 와 같은 기준으로 API 대기(FLAG-04).
5. D 예상 금액·수수료·거래세와 F 리스크 경고는 서버 계산이 필요하다. 서버 계산이 없으면 두 영역을 빼고 확인 단계에 «체결 금액은 체결 후 확정됩니다»만 보인다 → FLAG-04. 호가단위가 필요한 ±1틱 버튼·호가단위 검증과 빠른 비율 버튼도 같은 이유로 API 대기.
6. E 미체결 표: 1단계는 «출처»·«전략명» 열을 숨긴다(모두 수동). 정정 API 가 없어(FLAG-08 대조) «취소»만 둔다.
7. E 부분 체결(PARTIAL) 행: 체결수량/주문수량 진행 막대 + «남은 수량 N» 보조 문구 `재기획 1단계`.
8. 비활성 계좌는 폼 전체 비활성 + 사유(feature-spec EDGE-04).
9. 상태: v2 §5-16 그대로. 갱신 주기는 FLAG-07 가정(주문 5초 폴링 + 체결 SSE).
10. A 종목 헤더는 현재가와 기준 시각만 둔다(수집 중인 종목, `/api/market/features`). 전일대비·시가·고가·저가·거래량·거래대금·52주·베타·섹터와 B 10단계 호가, C 최근 체결 틱은 API 가 없어(FLAG-08 대조) API 대기.

## 7. 거래 내역 (1단계)

v2 §6 을 기준으로 아래를 바꾼다.

1. A 필터의 «출처»와 주문 이력의 «전략 선택»은 3단계에 붙인다.
2. B KPI 의 «전략 자동 비중»은 3단계에 붙인다. 1단계 KPI 5개는 집계 API 가 없어 API 대기(합산은 FLAG-04 상 화면 계산 불가).
3. C-1 주문 이력에 «메모» 열(왼쪽, 말줄임, 펼침 시 전체) 추가 → FLAG-13. «사유» 열(거부 사유)과 합계 행은 API 대기.
4. C-1 행 펼침에 상태 이력(접수 → 부분 체결 → 체결 완료/취소/거부, 각 시각)을 보인다 `보강`(CLAUDE.md «상태 전이는 명시적·추적 가능»). 상태 이력 API 가 없어 API 대기. 연결 체결 목록(v2 §6-11)은 1차 구현에 둔다.
5. C-2 체결 이력 탭은 1차 구현에서 뺀다(계좌 단위 체결 목록 API 대기, FLAG-21). 체결은 C-1 행 펼침의 연결 체결 목록으로 본다.
6. C-3 종목별 손익 탭은 API 가 없어 API 대기(«전략 자동 비중» 열은 3단계).
7. D 내려받기: 주문 이력 탭에서 받은 값 그대로 CSV 로 내려받는다(development-plan §8-3 AS-08).
8. 상태: v2 §6-13 그대로.

## 8. 수집 현황·구독 관리 (0단계)

탭 2개: «수집 현황» / «구독 관리».

1. 수집 현황 탭: v2 §13 기준. 확인된 API 는 `status`·`ingest-health`·`routing-status`·`KisWsHealth` 🟢. Upbit 소스 카드, C 지연 시계열, D Redis 최신가, E PostgreSQL 적재, F 이벤트 버퍼, G 오류 로그는 API 가 없어 원칙 6대로 뺀다(§11).
2. 구독 관리 탭: 소스 선택(KIS 실시간 / Upbit / 일봉 pykrx·yfinance / 거시 FRED) 후 같은 틀을 쓴다 `보강`.
   - 상단: 소스·채널(WS/REST) 선택, 구독 수, 연결 상태 요약
   - 좌: 카탈로그 검색(이름·코드·시장·구독 상태 필터, 20건씩 더보기)
   - 우: 구독 중 목록(해지 버튼)
   - 해지는 확인 단계를 거친다. 기존은 확인 없음(기존 목록 §222) `보강`
   - 카탈로그 동기화·일봉 일괄 수집은 «작업» 메뉴에 두고, 실행 결과(성공/실패 건수)를 표시
   - API 🟢(collector-api 의 `/api/{pykrx|yfinance}/symbols/*`, KIS·Upbit 구독, FRED. 일봉 일괄 수집은 quant-worker `/collect/daily`). 응답 모양 대조 완료(development-plan §4-1)
3. 상태: 각 영역 4상태. 구독 변경 결과는 토스트(«구독했습니다» / «요청 실패: 사유»).
4. 거시경제 지표 «관측치 보기»는 이 화면에 두지 않는다. 재기획 7장 5번 가정대로 분석 에이전트(거시)로 옮긴다.

## 9. 포트폴리오·성과 (1단계)

탭 2개: «포트폴리오» / «세금 요약».

1. 포트폴리오 탭: v2 §4 기준. 확인된 API 는 `daily-balances`·`portfolio-snapshots` 🟢. 1차 구현은 A KPI·B 자산 추이만 둔다. C 기간 수익률은 서버 값이 없어 API 대기(FLAG-16). A 의 총자산·현금·총 손익은 일별 잔고 마지막 행 값을 기준일과 함께(FLAG-19), 포지션 수는 포지션 개수, 투자금액은 API 대기. B 는 그래프 좌표만 숫자로 바꾸고 라벨·툴팁은 서버 원문(FLAG-17). 섹터 비중·기여도·위험 지표(베타·VaR·MDD·집중도)는 API 대기.
2. 세금 요약 탭: 연도 선택(최근 6년), 요약 표, «세금 재계산»(확인 단계 + 상태 READY/RUNNING/FAILED). API 🟢 `/api/accounts/{id}/tax-summaries/{year}`(접두사가 `/api/v1` 아님, 기존 목록 §85). 요약 표 열은 서버 응답 필드(실현 손익 합계·과세 대상 손익·예상 세액·상태·계산 시각)를 따른다(FLAG-08 대조).
3. 상태: v2 §4-10 그대로 + 세금 탭 FAILED 시 오류 줄 + 재계산.
