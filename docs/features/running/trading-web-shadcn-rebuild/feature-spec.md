## 3. 기능 목적

- **사용자/액터:** 개인 사용자 1인(트레이더 겸 전략 승인자). 로그인·역할 없음(현 상태). `스펙`
- **사용자 문제:** 기존 화면은 패딩·크기가 깨져 있고 정보 구조가 기능 나열식이다. 제품이 «모의투자 위 투자 실험실»로 재정의돼 화면도 단계에 맞춰 다시 짜야 한다. `스펙`(사람 말·재기획)
- **비즈니스 의도:** 토스처럼 간결하고 전문적인 화면을 shadcn/ui(Tailwind)로 처음부터 다시 만든다. 첫 범위는 0단계(브로커 연동 상태)와 1단계(모의투자 원장) 화면이다. `스펙`
- **원칙:** AI 는 주문을 직접 실행하지 않는다. 사람이 승인한 전략만 운영된다. 0·1단계엔 전략·AI 화면이 없지만, 이 원칙은 3·5단계 화면에 그대로 적용한다(RULE-01·02). `스펙`(README)
- **안 만드는 것 (non-goal):**
  - 기존 `frontend/trading-web` 의 디자인(토큰·스타일·컴포넌트)을 참고하거나 가져오는 것 `스펙`(사람의 절대 지시)
  - 거래 일지 화면 `스펙`(인계 §3). 투자 로그(왜 샀나)는 거래 내역 메모로 둔다(FLAG-13)
  - 실계좌 주문 화면 `스펙`(재기획 7장 9번: 실주문은 마지막 단계)
  - 2단계 이후 화면(시뮬레이션·전략·분석·AI) — 그 단계 착수 때 `스펙`(재기획 4장, v3 원칙 1)
  - 백엔드 API 신규 구현 `스펙`(FLAG-01: 백엔드는 나중). 필요한 API 는 §7 로 요구만 적는다
  - 토스 연동 구현 `스펙`(다른 세션 몫). 이 기능은 그 결과를 보여주기만 한다

## 4. 사용자 흐름 (0·1단계)

| 단계 | 사용자 행동 | 시스템 동작 | 결과 상태 |
|---|---|---|---|
| 1 | 브로커 연동 화면에서 KIS 모의 연동 상태를 본다 | KIS 시세 WebSocket 상태와 KIS 모의 연결 계좌 조회 결과 표시. 토큰 상태·호출 오류·토스는 API 대기(v3 §11) | 연동 확인 `스펙`(재기획 0단계) |
| 2 | 토큰이 만료됐으면 «토큰 재발급»을 누른다 | 서버가 재발급, 진행 중 표시, 결과 갱신. 토큰 재발급 API 가 없어 1차 구현에선 뺀다(v3 §11) | 연동 복구 `보강` |
| 3 | 수집 현황에서 시세가 들어오는지 보고, 구독 관리에서 종목을 구독·해지한다 | 소스별 연결·지연, 구독 변경(해지는 확인 단계) | 시세 수신 `스펙` |
| 4 | 상단 바에서 계좌(LOCAL·KIS 모의)를 고르고 홈에서 자산·손익·연동 상태를 본다 | 홈 요약(KPI·연동·수집 상태·자산 추이). 총자산·누적 손익은 일별 잔고 기준일 값(FLAG-19) | 현황 파악 `스펙` |
| 5 | 주문 화면에서 현재가를 보고 수동 주문을 낸다 | 입력 검증 → 확인 단계(매도는 잠길 수량 포함) → 제출(멱등키) → 체결 시 토스트·미체결 표 갱신. 호가·체결 틱·메모는 API 대기 | 주문 생성 `스펙` |
| 6 | 계좌·포지션에서 예수금·홀드·잠금 수량과 포지션을 보고, KIS 모의 계좌면 원장 대사 결과를 확인한다 | 불일치 목록은 표시만, 자동 수정 없음. 확인 처리는 API 대기(FLAG-18) | 원장 확인 `스펙`(재기획 1단계) |
| 7 | 거래 내역에서 주문 이력과 주문별 체결을 본다 | 필터·펼침. 체결 이력 탭·종목별 손익·상태 이력·메모는 API 대기(FLAG-21, v3 §11) | 복기 `스펙` |
| 8 | 포트폴리오·성과에서 자산 추이·세금 요약을 본다 | 세금 재계산은 확인 단계. 기간 수익률은 API 대기(FLAG-16) | 성과 확인 `스펙` |

## 5. 화면 상태

화면별 영역·열·문구는 [screen-spec-v3.md](./screen-spec-v3.md) 와 그것이 참조하는 v2 절이 정의하며 이 명세의 일부로 구속한다(복사하지 않음). 아래는 공통·교차 상태다.

출처 칸은 한 단어(`스펙`·`보강`·`물어봄`)만 쓴다. 물어서 확정된 것은 `스펙`으로 올리고 근거 칸에 FLAG 번호를 적는다.

## 6. 정책·규칙

| ID | 규칙 | 적용 대상 | 출처 | 근거 | 틀리면 impact |
|---|---|---|---|---|---|
| RULE-01 | AI 는 주문을 직접 실행하지 않는다. «운영중»이 아닌 전략에는 항상 «주문 불가»를 붙인다 | 3·5단계 전략·AI·사건 화면 (0·1단계 해당 없음) | 스펙 | README AI 원칙 | 높음 |
| RULE-02 | «승인» 버튼은 사람만 누르는 영역에 두고, 승인 이력에 승인자(설정된 운영자 이름)·시각을 남긴다 | 5단계 AI 전략 연구 (0·1단계 해당 없음) | 스펙 | README, FLAG-03 확정 | 높음 |
| RULE-03 | 금액·수량·가격·수수료는 문자열로 다루고(서버가 JSON 숫자로 보내도 원문 문자열로 보존해 받는다), 화면 계산에 부동소수점(`Number`·`parseFloat`)을 쓰지 않는다. 금액 계산은 서버 값만 쓰고, 차트 지표만 표시 전용으로 화면 계산을 허용한다. 예외: 자산 추이 그래프의 좌표 계산에만 숫자 변환을 허용한다(변환 함수 한 곳, 라벨·툴팁·축 문구는 서버 원문 문자열) | 모든 금융 값 | 스펙 | CLAUDE.md «Financial Safety», FLAG-04·17 확정 | 높음 |
| RULE-04 | 주문 요청은 폼마다 새 멱등키를 쓰고, 제출 중 중복 제출을 막는다 | 주문 | 스펙 | CLAUDE.md, 기존 목록 §5 | 높음 |
| RULE-05 | 등락·손익·매수/매도는 색 외에 부호(+/-)와 텍스트를 항상 병기한다. 한국식 상승=up·하락=down. 매수/매도 톤과 손익 톤은 분리한다 | 전 화면 | 스펙 | v2 공통 규칙 | 중간 |
