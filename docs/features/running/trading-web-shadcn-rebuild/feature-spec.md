## 3. 기능 목적

- **사용자/액터:** 개인 사용자 1인(트레이더 겸 전략 승인자). 로그인·역할 없음(현 상태). `스펙`
- **사용자 문제:** 기존 화면은 패딩·크기가 깨져 있고 정보 구조가 기능 나열식이다. 제품이 «모의투자 위 투자 실험실»로 재정의돼 화면도 단계에 맞춰 다시 짜야 한다. `스펙`(사람 말·재기획)
- **비즈니스 의도:** 토스처럼 간결하고 전문적인 화면을 shadcn/ui(Tailwind)로 처음부터 다시 만든다. 첫 범위는 0단계(브로커 연동 상태)와 1단계(모의투자 원장) 화면이다. `스펙`
- **원칙:** AI 는 주문을 직접 실행하지 않는다. 사람이 승인한 전략만 운영된다. 0·1단계엔 전략·AI 화면이 없지만, 이 원칙은 3·5단계 화면에 그대로 적용한다(RULE-01·02). `스펙`(README)
- **안 만드는 것 (non-goal):**
  - 기존 `frontend/trading-web` 의 디자인(토큰·스타일·컴포넌트)을 참고하거나 가져오는 것 `스펙`(사람의 절대 지시)
  - 거래 일지 화면 `스펙`(인계 §3). 투자 로그(왜 샀나)는 거래 내역 메모로 둔다(FLAG-13)
  - 실계좌 주문 화면 `스펙`(재기획 7장 9번: 실주문은 마지막 단계)
  - 2단계 이후 화면(시뮬레이션·전략·분석·AI) — 그 단계 착수 때 `스펙`(재기획 4장, v3 원칙 1)
  - 백엔드 API 신규 구현 `스펙`(FLAG-01: 백엔드는 나중). 필요한 API 는 §7 로 요구만 적는다
  - 토스 연동 구현 `스펙`(다른 세션 몫). 이 기능은 그 결과를 보여주기만 한다

## 4. 사용자 흐름 (0·1단계)

| 단계 | 사용자 행동 | 시스템 동작 | 결과 상태 |
|---|---|---|---|
| 1 | 브로커 연동 화면에서 KIS 모의·토스 연동 상태를 본다 | 브로커별 토큰·채널 상태, 연결 계좌 조회 결과, 최근 호출 오류 표시 | 연동 확인 `스펙`(재기획 0단계) |
| 2 | 토큰이 만료됐으면 «토큰 재발급»을 누른다 | 서버가 재발급, 진행 중 표시, 결과 갱신 | 연동 복구 `보강` |
| 3 | 수집 현황에서 시세가 들어오는지 보고, 구독 관리에서 종목을 구독·해지한다 | 소스별 연결·지연, 구독 변경(해지는 확인 단계) | 시세 수신 `스펙` |
| 4 | 상단 바에서 계좌(LOCAL·KIS 모의)를 고르고 홈에서 자산·손익·연동 상태를 본다 | 홈 요약 6영역 | 현황 파악 `스펙` |
| 5 | 주문 화면에서 호가·체결을 보고 메모와 함께 수동 주문을 낸다 | 입력 검증 → 확인 단계(홀드될 금액 포함) → 제출(멱등키) → 체결 시 토스트·미체결 표 갱신 | 주문 생성 `스펙` |
| 6 | 계좌·포지션에서 예수금·홀드·잠금 수량과 포지션을 보고, KIS 모의 계좌면 원장 대사 결과를 확인한다 | 불일치는 표시만, 자동 수정 없음 | 원장 확인 `스펙`(재기획 1단계) |
| 7 | 거래 내역에서 주문·체결·종목별 손익과 메모·상태 이력을 본다 | 필터·탭·펼침 | 복기 `스펙` |
| 8 | 포트폴리오·성과에서 자산 추이·기간 수익률·세금 요약을 본다 | 세금 재계산은 확인 단계 | 성과 확인 `스펙` |

## 5. 화면 상태

출처 칸은 한 단어(`스펙`·`보강`·`물어봄`)만 쓴다. 물어서 확정된 것은 `스펙`으로 올리고 근거 칸에 FLAG 번호를 적는다.

## 7. 데이터·API 요구 (0·1단계)

«소유»는 현재 백엔드에서 확인한 것이다. 확인 범위는 §2 참조. 🟠 항목은 백엔드 작업 때 넘길 요구다(이 기능은 구현하지 않음).

| 필요 | 데이터·API | 화면 | 현황 | 출처 | 근거 |
